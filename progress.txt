=== Iteration 3 - S3 - 2026-01-29 ===
Status: COMPLETE
Learnings:
- @block32/jwt-auth package uses JwtModule.forRoot() with JwtBlock32Options
- accessToken options require storage type ('header' or 'cookie') and keyOptions
- refreshToken always uses cookie storage with RefreshCookieOptions (httpOnly: true, sameSite: 'strict')
- JwtSyncService provides signAccessSync, signRefreshSync, verifyAccessSync, verifyRefreshSync methods
- TokenService provides setAccessTokenToStorage, setRefreshTokenToStorage, getAccessTokenFromStorage, getRefreshTokenFromStorage
- For header storage, use headerOptions with headerName and prefix
- For cookie storage, use cookieOptions with cookieName, httpOnly, secure, sameSite, path, maxAge
- Mock users can be simple in-memory array for testing purposes
- RSA keys generated with: openssl genrsa -out private.pem 2048 && openssl rsa -in private.pem -pubout -out public.pem
- NestJS controllers need @Res({ passthrough: true }) to set cookies while also returning a body

=== Iteration 4 - S4 - 2026-01-29 ===
Status: COMPLETE
Learnings:
- JwtSyncGuard and JwtAsyncGuard are exported from @block32/jwt-auth
- Guards only verify token validity and return true/false, they don't attach payload to request
- To get user payload in protected routes, need to manually call tokenService.getAccessTokenFromStorage() and verify
- JwtAsyncGuard uses jwtAsyncService.verifyAccessAsync() which returns a Promise
- JwtSyncGuard uses jwtSyncService.verifyAccessSync() which returns synchronously
- ProtectedModule needs to import AuthModule to get access to JWT services (they are provided by JwtModule which is imported in AuthModule)
- @UseGuards(JwtSyncGuard) and @UseGuards(JwtAsyncGuard) decorators work with NestJS guard system

=== Iteration 7 - S7 - 2026-01-29 ===
Status: COMPLETE
Learnings:
- Custom errors are exported from @block32/jwt-auth: SecretKeyError, UndefinedTokenError, WrongAuthHeaderTypeError, EmptyCookieError, RefreshTokenError
- ErrorsController uses HttpException to return structured error responses {error: 'ErrorClassName', message: '...'}
- For WrongAuthHeaderTypeError and EmptyCookieError, the errors are triggered naturally by calling tokenService methods without proper headers/cookies
- SecretKeyError and RefreshTokenError are manually thrown since they require specific configuration conditions not easily triggered via endpoints

- TokenService.getAccessTokenFromStorage() throws WrongAuthHeaderTypeError when Authorization header is missing (for header storage)
- TokenService.getRefreshTokenFromStorage() throws EmptyCookieError when refresh cookie is missing
